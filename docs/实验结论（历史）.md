# Droidspaces 内核补丁（droid_lkm）阶段结论 · 今晚收尾版

> 设备：Redmi Pad Pro（dizi / SM7435，KSU 临时 ROOT，GKI `android12-5.10`，`5.10.236-android12-9-00003-gfb24cf99ad97-ab14313284`）
> 最后更新：2026-11-05 23:55
> 现场状态：config 509 B / `5e586287…`、`custom_init` 计数 0；无 `keepalive.sh`；无模块加载；无残留挂载/网卡/iptables

## 0. 一句话结论

**复位触发点已缩到"容器 PID1 死亡"这一个动作，且与 CLI 收尾、与 ns 引用计数都无关：**

| 动作 | 结果 |
|---|---|
| A 版 plain `start`（init=`/sbin/init`，systemd） | **稳定 ×3** |
| `kill -TERM <容器 PID1>` | **不崩**（uptime 124→145 单调；容器仍 `RUNNING`，`run -- /bin/echo alive` 正常） |
| **`kill -KILL <容器 PID1>`** | **立即复位**（uptime 179.04 → 新 boot_id、uptime 12 s） |
| `droidspaces stop`（systemd 容器） | 复位，日志停在 `Waiting for graceful shutdown` |
| B5 `pin_kref=1 no_teardown=0` + `stop` | 同一行崩 ⇒ **钉住 pid ns 引用计数无效** |

⇒ 致命路径 = **容器命名空间里最后一个任务（PID1）真正退出时**，内核的退出/回收链（`zap_pid_ns_processes` / `release_task` / nsproxy 释放）碰到我们伪造的 ns 结构。CLI 的 unmount、net teardown、monitor 退出都不在致命链上（TERM 那发什么都没做、也没崩）。

**另一条今晚顺手查清的"假崩"**：`--init=/keepalive.sh` 的 start 崩溃**不是模块问题**——那个脚本 shebang 写的是 `#!/system/bin/sh`，而 Ubuntu rootfs 里没有 `/system/bin/sh`（只有 `/bin/sh -> dash`），exec 直接失败 ⇒ PID1 秒死 ⇒ 命中同一条致命路径。**以后 keepalive 脚本必须用 `#!/bin/sh`。**

## 4. 未解决：PID1 死亡→复位 的精确内核动作

已排除：CLI 收尾（§2.1 TERM 不崩）、pid ns 引用计数归零（§2.3 pin_kref 无效）、journal/落盘、钩子（B5 零钩子仍崩）、环境漂移。

剩余候选（明天按代价排序）：

1. **`pin_reaper`**：内核在 `forget_original_parent` 里，若 `task == ns->child_reaper` 就对本 ns 调 `zap_pid_ns_processes(ns)`。我们伪造 ns 的 `child_reaper` 指向容器 PID1，它一死就必然进入 zap —— 而 zap 会碰 `ns->ucounts`（伪造 ns 里是 NULL）、`pid_allocated`、idr。**B4 已编译好且从未上机，`pin_reaper=1 park_hook=0` 是明天第一发（不用重编）。**
2. **伪造的 IPC ns 释放**：`free_nsproxy` 除了 `put_pid_ns` 还会 `put_ipc_ns` → `free_ipc_ns`（`shm_exit_ns/sem_exit_ns/msg_exit_ns` + `put_user_ns`）。`pin_kref` 只钉了 pid ns，**没有钉 ipc ns**，这条完全没被覆盖过。
3. `destroy_pid_namespace` 里的 `dec_pid_namespaces(ns->ucounts=NULL)`。

## 6. KSU zip 为什么不装

**不装。** PID1 死亡即复位还没解决，固化成开机自启 = 每次停容器都重启整机。A 版可提供服务，只要**不主动停容器、也不强杀容器内进程**。

## 10. 最后一发：kmsg 流式抓取成功，但复位是"静默硬件级"

### 10.1 日志通道现状

| 通道 | 结果 |
|---|---|
| `/proc/sys/kernel/dmesg_restrict` | `0`（允许读） |
| `dmesg` CLI | **输出为空**（0 行），不可用 |
| **`cat /proc/kmsg`** | **可读**，能拿到完整 printk（用 `echo "<6>MARKER" > /dev/kmsg` 校正，marker 被捕获 ⇒ 流式采集有效） |
| `/proc/last_kmsg` | 512 KB 固定区，**尾部全是 0xFF 垃圾**，不含上次崩溃，无用 |
| `/sys/fs/pstore` | Permission denied（SELinux，`u:r:ksu:s0` 也拒） |
| `panic_on_warn / panic_on_oops / panic(= -1)` | `0 / 1 / -1` ⇒ **panic 不会自动重启（-1 = 永久挂起）** |

**关键推论**：设备确实重启了，而 `panic=-1` 下内核 panic 只会挂死不会重启 ⇒ 这 12 次复位**不是内核 panic**，而是**无 printk 的静默硬件级复位**（watchdog 咬 / SError）。堆栈抓不到是必然的。

### 10.2 抓到的模块内证据（B4，`park_hook=0 pin_reaper=1 no_zap=1`）

启动正常、容器 normal：

```
[  110.867827] [droid_lkm] syscall slots patched: unshare=97 reboot=142
[  111.221122] [droid_lkm/dbg] pidns 00000000ba988147 created level=1 inum=4026534621 parent=0000000086304620 reaper=0000000074d72cd2
[  111.222695] [droid_lkm/dbg] keepalive: pinned, rmmod will -EBUSY
```

`kill -KILL <PID1>` 之前一刻的容器内任务退出洪水（**全部 `reaper=0`**）：

```
[  226.691000] [droid_lkm/dbg] exit_ns: (sd-close)[17407] ns=00000000c3617e51 reaper=0
[  226.768930] [droid_lkm/dbg] exit_ns: polkit-kde-auth[17413] ns=00000000c3617e51 reaper=0
...
[  112.009616] [droid_lkm/dbg] park: ns=00000000a63b915b alloc=2147483663 comm=systemd-factory
```

**`alloc=2147483663` 是本轮最重要的数字**：`0x8000000F` = **`PIDNS_HASH_ADDING`（bit31）仍然置位 + 只有 15 个 PID**。也就是说，我们伪造的 pid ns 一直带着"哈希表正在加入"标志，`pid_allocated` 永远不可能归零。内核在 ns 空掉时做的等待/回收（`zap_pid_ns_processes` 的 `while (pid_ns->pid_allocated)` 一类）会**死循环**，随后被 watchdog 静默复位 —— 这正好解释"无 printk、无栈、几秒内重启"。

### 10.3 由此得出

- 之前所有"堵释放路径"的思路（`pin_kref` / `no_teardown` / `pin_reaper` / `park_hook`）**全都无效**，因为它们解决的是"释放"，而真正的问题是**伪造 ns 的内部计数从一开始就是错的**（`PIDNS_HASH_ADDING` 未清、`pid_allocated` 与实际 PID 数不符）。
- 明天第一件事不是再加钩子，而是**在 `pidns_create` 里把伪造 ns 的内部状态改成内核认得的"干净初始化态"**：
  1. `pid_allocated` 清零、**确保 `PIDNS_HASH_ADDING` 位不置位**（或按内核 `alloc_pid` 的真实流程让它走完 `pid_ns->idr` 的 add）；
  2. `ucounts` 置为父 ns 的（而不是 NULL）；
  3. `child_reaper` 指向一个**永不退出的**内核任务（`init_task`，B4 的 `pin_reaper` 已证明不够，因为计数问题不在 reaper）。
- 验证探针依旧用 `kill -KILL <容器 PID1>`（比 `stop` 快、日志干净），配合 `cat /proc/kmsg` 落到宿主文件（本次已验证：`kmsg_host_B4.log` 抓到 1.7 MB，重启后文件仍完好）。
